## 2026-10-24 - Windowed identical-repeat escalation (senpi#3641)

### What changed

- `detectors.ts` adds `detectWindowedRepeat` plus `windowedRepeatCount`/`windowedOverThreshold`: cumulative occurrences of the last call's exact signature (tracked since the most recent non-observing call, unbounded by the call window) at or above `policy.ts WINDOWED_REPEAT_THRESHOLD = 8` produce an `identical` detection with `windowed: true` (the consecutive detector reports `windowed: false` and runs first). Only calls from known-observing tools (`policy.ts OBSERVING_TOOL_NAMES`: read/ls/glob/grep/todo/todo_view/webfetch/web_search/bash_output/task_output/lsp_*) keep the count alive between repeats; every other tool — computer, MCP/browser tools, task*, unknown extensions — resets it, so click→screenshot sessions never arm while #3629's todo-interleaved eval loop keeps counting.
- `NoticeGate` keys split consecutive from windowed (`identical:c` vs `identical:w`): a windowed entry survives while its cumulative count is over the windowed threshold — the count cannot flap at the window edge and cannot stall below the doubling threshold at wider repeat spacing (the 8 → 16 doubling holds at every spacing), while a consecutive entry expires on any break exactly as on main (a burst, an edit, a new run still notifies at 3; pinned by test).
- `escalation.ts` keeps windowed episodes per fingerprint (two interleaved loops escalate independently); a pattern change clears only the consecutive episode, and `hasActiveEpisodes()` gates the release of recovery/hold state in `index.ts` so it happens only when no episode of either kind remains.
- `notice.ts` adds the windowed identical reminder (no "in a row" phrasing, no "change one parameter" advice; a polling-specific intro for `POLLING_TOOL_NAMES`); `renderer.ts` renders the windowed expanded line.

### Why

- senpi#3629: one identical `eval` call repeated 455+ times across a 7-day session. `detectIdenticalRun` counts only the trailing consecutive run, so todo/read interleaves kept the run at 1 and nothing fired; `detectCycle` sees only periods ≤ 6 and similar/cycle detections never arm blocks (#2905); the escalation episode reset on any different-signature call. `WINDOWED_REPEAT_THRESHOLD = 8` sits above the observed legitimate repeat ceiling (6 identical eval calls in a 2026-09-19 fixture) and far below every incident count (197 / 455+ / 655).

### Why an extension could not handle it

- The builtin owns the private tracker, detector and escalation state and the `tool_call` veto; no public API exposes them.

### Expected merge conflict zones

- MEDIUM: `detectors.ts` (detection union, gate keys), `escalation.ts` (episode map). LOW: `policy.ts`, `index.ts`, `notice.ts`, `renderer.ts`, the two test files. NONE: public extension APIs.

### Fixed
- Loop guard now stops an identical tool call repeated non-consecutively, the shape of an interleaved loop that previously repeated one call hundreds of times: repeats count only while the calls between them come from known-observing tools, so computer-use click→screenshot sessions never arm; a warning fires at the 8th such repeat, a second at the 16th (the count is cumulative since the last non-observing call, so wider repeat spacing cannot stall it), the next identical call is blocked, and a hard stop follows three blocked attempts; two interleaved loops escalate independently, and the consecutive ladder keeps its exact previous timing ([#3629](https://github.com/code-yeongyu/senpi/issues/3629)).
